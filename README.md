# LLM Engineering – Insurellm RAG Assistant

A Retrieval-Augmented Generation (RAG) assistant that answers questions about the fictional company **Insurellm**, plus an evaluation suite that measures how well it retrieves information and answers questions.

The project has three parts:

1. **Ingestion** (`rag/ingest.py`) reads the markdown files in the knowledge base, splits them into chunks, turns each chunk into an embedding vector, and stores everything in a local Chroma vector database.
2. **Chat app** (`rag/app.py`) is a Gradio web UI. For each question it retrieves the most relevant chunks from the vector database and sends them, with the question, to an LLM to produce an answer. The retrieved context is shown beside the chat.
3. **Evaluations** (`evals/`) run a set of test questions through the system and score both the retrieval step (MRR, nDCG, keyword coverage) and the final answers (an LLM judge scores accuracy, completeness and relevance).

## Prerequisites

- **macOS, Linux or Windows** with a terminal
- **[uv](https://docs.astral.sh/uv/)** (Python package and environment manager)
- **Python 3.12** (uv can install it for you)
- **An OpenAI API key.** It is used by the chat model in `answer.py` and by the LLM judge in the evals.
- An internet connection for the first run. The embedding model (`all-MiniLM-L6-v2`) is downloaded from Hugging Face the first time and cached after that.

Install uv if you don't have it:

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# or with Homebrew
brew install uv
```

## Setup

### 1. Go to the project root

```bash
cd path/to/llm_engineering
```

All commands in this README are run from this folder.

### 2. Make sure Python 3.12 is used

```bash
uv python install 3.12
uv python pin 3.12
```

`pyproject.toml` must allow Python 3.12. Check it contains:

```toml
requires-python = ">=3.12"
```

If it says `>=3.14`, change it to `>=3.12`. Some AI libraries (such as PyTorch, which `sentence-transformers` depends on) may not yet have working builds for very new Python versions.

### 3. Install dependencies

```bash
uv sync
```

This creates `.venv/` and installs everything listed in `pyproject.toml`. If any package is missing, add it. For example:

```bash
uv add sentence-transformers
```

The libraries this project relies on include:

| Package | Purpose |
|---|---|
| `langchain-core`, `langchain-openai` | LLM wrapper and message types |
| `langchain-chroma`, `chromadb` | Vector database |
| `langchain-huggingface`, `sentence-transformers` | Local embedding model |
| `langchain-text-splitters`, `langchain-community` | Splitting and loading documents |
| `gradio` (version below 6) | Web UI for the chat app and the eval dashboard |
| `litellm` | Calls the LLM judge in the evals |
| `pydantic` | Data models for test cases and scores |
| `pandas` | Tables and charts in the eval dashboard |
| `python-dotenv` | Loads variables from `.env` |
| `pytest` (dev) | Running the tests |
| `ipykernel` (dev, optional) | Running notebooks |

Install any that are missing, for example:

```bash
uv add litellm pandas
uv add --dev pytest ipykernel
```

### 4. Pin Gradio below version 6

The UI code in this project is written for Gradio 5.x. Gradio 6 changed several parameters (for example `type` on `gr.Chatbot`, and `theme` moving from `gr.Blocks()` to `launch()`), so pin it:

```bash
uv add "gradio<6"
```

### 5. Add your API key

Create a file named `.env` in the project root:

```bash
OPENAI_API_KEY=sk-your-key-here
```

Optional, to avoid Hugging Face rate-limit warnings when downloading the embedding model:

```bash
HF_TOKEN=hf_your-token-here
```

Never commit `.env` to git. Make sure `.gitignore` contains it:

```
.env
.venv/
data/vector_db/
data/eval_results/
__pycache__/
```

You can also keep a `.env.example` in the repo with variable names only:

```
OPENAI_API_KEY=
HF_TOKEN=
```

## Configuration

Shared settings live in `src/llm_engineering/config.py`. The ingestion, answering and eval code all import from it, so the paths and models always match.

```python
from pathlib import Path

# config.py -> llm_engineering -> src -> project root
ROOT = Path(__file__).resolve().parents[2]

DATA_DIR = ROOT / "data"
KNOWLEDGE_BASE = DATA_DIR / "knowledge-base"
DB_NAME = str(DATA_DIR / "vector_db")

EVALS_DIR = DATA_DIR / "evals"
TEST_FILE = EVALS_DIR / "tests.jsonl"

EMBEDDING_MODEL = "all-MiniLM-L6-v2"
JUDGE_MODEL = "openai/gpt-6-luna"   # set to a model your account can use
```

**Important:** the embedding model used to build the database must be the same one used to query it. If they differ, you will see an error like `Collection expecting embedding with dimension of 1536, got 384`. If you change `EMBEDDING_MODEL`, delete the database and re-run ingestion (see [Rebuilding the database](#rebuilding-the-database)).

Other settings in the code:

| Setting | File | Meaning |
|---|---|---|
| `chunk_size=500`, `chunk_overlap=200` | `rag/ingest.py` | How documents are split |
| `RETRIEVAL_K = 10` | `rag/answer.py` | Number of chunks retrieved per question |
| `MODEL` | `rag/answer.py` | The OpenAI chat model name. Set this to a model your account can access |
| `JUDGE_MODEL` | `config.py` | The model that grades answers in the evals |

## Step 1 – Build the vector database

Run this **once**, and again whenever the documents in `data/knowledge-base/` change.

```bash
uv run python -m llm_engineering.rag.ingest
```

### What it does

1. Looks inside each subfolder of `data/knowledge-base/` and loads every `.md` file.
2. Adds a `doc_type` metadata tag to each document (`company`, `contracts`, `employees` or `products`).
3. Splits documents into chunks of 500 characters with 200 characters of overlap.
4. Embeds every chunk with the `all-MiniLM-L6-v2` model (384-dimension vectors).
5. Saves the chunks and vectors in a Chroma database at `data/vector_db/`.

### Expected output

You should see something like:

```
There are 123 vectors with 384 dimensions in the vector store
Ingestion complete
```

(The exact vector count depends on your documents.) The key things to check are that the count is above zero and that the dimension is **384**.

Warnings about `langchain-community` being sunset, Pydantic V1 or unauthenticated Hugging Face requests can be ignored for now.

### Verify the database exists

```bash
ls data/vector_db
```

You should see a `chroma.sqlite3` file and one or more folders.

## Step 2 – Run the chat app

After ingestion has finished:

```bash
uv run python -m llm_engineering.rag.app
```

Gradio will start a local server and open your browser, normally at <http://127.0.0.1:7860>. If the browser doesn't open, copy the URL from the terminal.

### Using the app

- Type a question in the **Your Question** box and press Enter, for example:
  - `Who is Avery?`
  - `What products does Insurellm offer?`
  - `Tell me about the contract with GreenField Holdings.`
- The conversation appears on the left.
- The retrieved context (the source chunks used for the answer) appears on the right, with the file each came from.

Conversation history is used when retrieving context, so follow-up questions work.

Stop the app with `Ctrl + C` in the terminal.

## Step 3 – Run the evaluations

The evals check how well the system finds the right information and how good its answers are. They need the vector database from Step 1 and a working `OPENAI_API_KEY`.

### The test questions

Test questions live in `data/evals/tests.jsonl`, one JSON object per line:

```json
{"question": "Who won the prestigious IIOTY award in 2023?", "keywords": ["Maxine", "Thompson", "IIOTY"], "reference_answer": "Maxine Thompson won the prestigious Insurellm Innovator of the Year (IIOTY) award in 2023.", "category": "direct_fact"}
```

| Field | Meaning |
|---|---|
| `question` | The question asked to the RAG system |
| `keywords` | Terms that should appear in the retrieved chunks. Used for retrieval scoring |
| `reference_answer` | The correct answer. The LLM judge compares the generated answer to it |
| `category` | Question type, for example `direct_fact`, `spanning` or `temporal`. Scores are averaged by category |

`src/llm_engineering/evals/dataset.py` loads and validates these (an `EvalCase` model). To add a case, append a new line to the file. Keep the file committed to git, since a good test set is valuable.

### What is measured

**Retrieval** (no LLM calls, fast and free apart from local embeddings):

| Metric | Meaning |
|---|---|
| MRR | Mean Reciprocal Rank. How high in the results the first chunk containing each keyword appears (1.0 = first place) |
| nDCG | Normalised Discounted Cumulative Gain. Rewards relevant chunks that rank higher |
| Keyword coverage | Percentage of the keywords found anywhere in the top-k chunks |

**Answers** (LLM judge, scores 1 to 5):

| Metric | Meaning |
|---|---|
| Accuracy | Is it factually correct compared to the reference answer? (a wrong answer scores 1) |
| Completeness | Does it include all the information in the reference answer? |
| Relevance | Does it answer the question directly without extra information? |

### Evaluate a single test

The argument is the row number in `tests.jsonl`, starting at 0:

```bash
uv run python -m llm_engineering.evals.evaluate 0
```

It prints the question, keywords and reference answer, then the retrieval scores, the generated answer, the judge's feedback and the three scores.

### Evaluate everything with the dashboard

```bash
uv run python -m llm_engineering.evals.dashboard
```

A Gradio page opens with two sections:

- **Retrieval evaluation:** average MRR, nDCG and keyword coverage, plus a chart of average MRR by category.
- **Answer evaluation:** average accuracy, completeness and relevance, plus a chart of average accuracy by category.

Click **Run Evaluation** in each section. Results are colour-coded: green is good, amber is acceptable, red needs work (for example, MRR below 0.75 or an answer score below 4.0 shows red).

**Cost and time:** the retrieval run makes no LLM calls and finishes quickly. The answer run makes two LLM calls per test (one to answer, one to judge), so it takes longer and costs a small amount, in proportion to the number of tests.

### Using the results

Change one thing at a time (chunk size, `RETRIEVAL_K`, embedding model, prompt) and re-run the evals to see whether it helped. If you change the chunking or embedding model, rebuild the database first (see [Rebuilding the database](#rebuilding-the-database)).

Reading the scores:

- Low retrieval scores with good answers when the right chunk is found means the problem is retrieval.
- A missing keyword in the retrieved chunks usually explains an incomplete or wrong answer, since the model only sees what was retrieved.
- Compare categories to find the kinds of question the system handles worst.

### Optional: explore in a notebook

If you like working interactively, keep a notebook in `notebooks/` that imports from the package, for example:

```python
from llm_engineering.evals.dataset import load_tests
from llm_engineering.evals.evaluate import evaluate_retrieval, evaluate_answer

tests = load_tests()
example = tests[0]
evaluate_retrieval(example)
eval_result, answer, chunks = evaluate_answer(example)
```

Select the project's `.venv/bin/python` as the notebook kernel. Keep the logic in the package and use the notebook only for looking at results.

The `tests/` folder holds pytest tests that check the code works (paths resolve, documents load, chunks are produced and so on). They are separate from the evals, which measure answer quality.

## How it works

```
data/knowledge-base/*.md
        │
        ▼  ingest.py
  load → split into chunks → embed (all-MiniLM-L6-v2) → store in Chroma
                                                          │
                                                   data/vector_db/
                                                          │
User question ──► app.py ──► answer.py                    │
                               │  combine prior user messages + new question
                               │  retrieve top-k similar chunks ◄─────────────┘
                               │  put chunks into the system prompt
                               ▼
                       OpenAI chat model ──► answer (+ context shown in the UI)


data/evals/tests.jsonl
        │
        ▼  evaluate.py / dashboard.py
  for each test:
    fetch_context()    ──► retrieval metrics (MRR, nDCG, keyword coverage)
    answer_question()  ──► LLM judge ──► accuracy, completeness, relevance
```

- `rag/ingest.py` – `fetch_documents()`, `create_chunks()` and `create_embeddings()`.
- `rag/answer.py` – `fetch_context()` retrieves chunks, `answer_question()` builds the prompt and calls the LLM.
- `rag/app.py` – the Gradio interface, which calls `answer_question()` for each message.
- `evals/dataset.py` – loads the test questions.
- `evals/evaluate.py` – retrieval metrics, the LLM judge, and the single-test command line.
- `evals/dashboard.py` – runs all tests and shows averages and per-category charts.

Delete the old database and run ingestion again when you:

- change `EMBEDDING_MODEL`
- change chunk size or overlap

```bash
rm -rf data/vector_db
uv run python -m llm_engineering.rag.ingest
```

## Troubleshooting

### `ValueError: Expected Embeddings to be non-empty list or numpy array, got [] in upsert`

No documents were loaded, so there were no chunks to embed. Check:

- `data/knowledge-base/` exists and contains the subfolders with `.md` files.
- `KNOWLEDGE_BASE` in `config.py` points to the right place. `ROOT` should be the project root (the folder containing `pyproject.toml`).
- You are not accidentally using an old relative path in `ingest.py`.

Quick check:

```bash
find data/knowledge-base -type f | wc -l
```

### `InvalidArgumentError: Collection expecting embedding with dimension of 1536, got 384`

The database was built with a different embedding model (1536 dimensions is typical of OpenAI embeddings) than the one you are querying with (384 for `all-MiniLM-L6-v2`). Delete `data/vector_db` and re-run ingestion, and make sure both `ingest.py` and `answer.py` import `EMBEDDING_MODEL` from `config.py`.

### `ModuleNotFoundError: No module named 'sentence_transformers'`

```bash
uv add sentence-transformers
```

If installation fails on a very new Python version, switch to Python 3.12 as described in [Setup](#setup).

### `The requested Python version 3.12 is incompatible with the project requires-python value of >=3.14`

Edit `pyproject.toml` and set `requires-python = ">=3.12"`, then run `uv python pin 3.12`, remove `.venv` and run `uv sync`:

```bash
rm -rf .venv
uv sync
```

### Gradio errors (`unexpected keyword argument`, theme warnings)

This project targets Gradio 5.x. If you see `Chatbot.__init__() got an unexpected keyword argument 'type'` or a warning that `theme` has moved to `launch()`, you have Gradio 6 installed. Check and pin the version:

```bash
uv pip show gradio
uv add "gradio<6"
```

To move to Gradio 6 instead, remove `type="messages"` (and `show_copy_button` if it errors) from `gr.Chatbot`, and pass `theme=` to `launch()` rather than `gr.Blocks()`. Don't mix the two styles.

### The app opens but answers are empty or say "I don't know"

- Check that `answer.py` uses `DB_NAME` from `config.py` (not a path built from `__file__`). A wrong path means the app reads an empty database.
- Check that `data/vector_db/` exists and was created by a successful ingestion.
- Look at the "Retrieved Context" panel. If it is empty, retrieval is failing. If it shows relevant text but the answer is wrong, the issue is in the model call.

### Model not found / unsupported parameter errors

The `MODEL` value in `answer.py` and `JUDGE_MODEL` in `config.py` must be models your OpenAI account can use. If the error mentions `reasoning_effort`, remove that argument (from `ChatOpenAI(...)` in `answer.py`, or the `extra_body` in the judge call in `evaluate.py`), since not every model accepts it.

### `ModuleNotFoundError: No module named 'litellm'` (or `pandas`)

```bash
uv add litellm pandas
```

### `FileNotFoundError` for `tests.jsonl`

Check that the file is at `data/evals/tests.jsonl` and that `TEST_FILE` in `config.py` points to it.

### Evals show low retrieval scores

Check which keywords are missing from the retrieved chunks. Try larger chunks, a higher `RETRIEVAL_K` or a stronger embedding model, rebuild the database, and re-run. Change one thing at a time so you can see what helped.

### `AuthenticationError` / missing API key

Check `.env` is in the project root and contains `OPENAI_API_KEY=...`, with no quotes or spaces around the `=`. Run from the project root so `load_dotenv` can find it.

### Warning: "You are sending unauthenticated requests to the HF Hub"

Harmless. Add `HF_TOKEN` to `.env` for higher rate limits.

### Imports fail with `ModuleNotFoundError: No module named 'llm_engineering'`

Run commands from the project root using `uv run python -m llm_engineering.<package>.<module>`, not `python ingest.py` from inside a subfolder. Also confirm `__init__.py` exists in `src/llm_engineering/` and in each package folder (`rag/`, `evals/`).

### Pytest warns about collecting a class starting with `Test`

pytest treats classes named `Test...` as test classes. The eval model is named `EvalCase` to avoid this. Keep that naming.

## Notes and tips

- Run everything from the project root so relative imports and `uv` pick up the right environment.
- Keep the `.env` file out of git, and rotate any API key that was ever committed.
- `data/vector_db/` and `data/eval_results/` are generated output and don't need to be committed. `data/evals/tests.jsonl` should be committed.
- The Chroma database is local. Deleting the `data/vector_db` folder resets it.
- To add new knowledge, put `.md` files into one of the subfolders of `data/knowledge-base/` (or add a new subfolder) and re-run ingestion. Then consider adding test questions for it to `tests.jsonl`.
- Keep a few test questions aside that you don't tune against, so your scores aren't inflated.
- The judge's scores depend on the judge model and its prompt. Don't compare scores across runs that used a different judge.
